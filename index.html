BEFORE YOU START

開始前先確認：wi-test、TFS Work Item Bundle、本機環境都有準備好。

白話說，就是 AI 要能讀 TFS 工項與討論、能開 Chrome 跑瀏覽器，也要能在測完後產生留言草稿給你確認。

01wi-test skill

AI 才知道「測 143117」要走哪個流程。

02TFS Work Item Bundle

讀工項、讀討論，並處理留言草稿與確認送出。

03Node.js 20+ / Chrome

runner 需要 Node.js；瀏覽器驗證會使用獨立 Chrome 設定檔。

04可連線站台

本機或測試機都可以；先確認要驗的站台能開啟。

專案已接過且 .agents 已上版控？ 下次通常可以直接使用，不需要重新「接上專案」；必要時重新登入測試用 Chrome 或跑 verify-config 檢查即可。

FIRST TIME

第一次接專案，建議由熟悉專案的工程師建立。

這一步不是個人偏好設定，而是在建立之後團隊共用的測試基準：站台網址、登入判定、錯誤畫面、測資慣例與專案特殊規則。

理由：如果初始設定判斷錯，後面的 plan.json 與回歸測試都會沿用同一套基準。由工程師先建好並上版控，其他人之後通常就能直接使用。

.agents 上版控

DAILY USE

最短其實可以只說：測 143117。

如果這張工項還沒有計畫，wi-test 會先規劃再執行；如果已經有 plan.json，就直接沿用既有計畫重跑。

TEST DATA

測試資料可能需要準備，但不是 runner 自己亂建。

wi-test 本體不直接建測資、不直接改資料庫。若某個情境需要固定資料，會依照專案自己的測資工具、script 或 skill 來處理；沒有就列為待補。

使用者要知道

要穩定重播，就要有穩定測資。測資不足時，結果可能需要人工補確認。

工程師要維護

測資慣例、seed script、測試帳號或特殊規則，應記在 project.md。

WHAT IT CHECKS

畫面看起來有字，不代表真的測到了。

例如圖表、報表或動態產生的資料，光看畫面文字有時不準。wi-test 會盡量改看「產生這個畫面的資料是不是正確」，不能穩定判斷的就列成人工驗收。

1

畫面有出現

確認基本操作有成功。

2

背後資料正確

比只看文字更可靠。

3

錯誤訊號

看是否有 console / HTTP 錯誤。

4

人工驗收

美感或業務判斷留給人。

SKILL SPLIT

對使用者是一句話；對工程師是 setup → plan → run 三段職責。

你說「測 143117」時，可以由 AI 依狀態決定：還沒接專案就 setup、沒有計畫就 plan、已有計畫就 run。

01
wi-test-setup

接上專案，只建立站台設定。通常第一次接專案才需要特別執行；之後多數情況可直接沿用。

02
wi-test-plan

讀工項與討論，建立 / 更新 plan.json，不執行。

03
wi-test-run

照計畫跑瀏覽器、產結果與留言草稿。

三段職責15 / 24
16 / 24
AFTER SETUP

第一次接上專案，主要產出兩份專案設定。

這兩份不是工具本體的一部分，而是這個專案自己的測試知識；建議跟著專案版控保存。

.agents/wi-test/site.json

給 runner 讀的結構化站台事實：環境網址、登入判定、錯誤偵測、等待訊號。

.agents/wi-test/project.md

無法塞進 schema 的專案知識：測資慣例、登入加速器、特有的坑、待補事項。

已接過的專案：只要 .agents/wi-test 已在 repo 裡，下次不用重新「接上線」。初始設定建議由工程師建立，是為了避免錯誤的站台網址、登入判定或專案規則被團隊持續沿用。
接上專案後16 / 24
17 / 24
AFTER RUNNING

測一張工項後，產物分成「進版控」與「不進版控」。

目的很簡單：規格與歷史要留下來，截圖與本次結果不要塞滿 Git。

進版控

.agents/tests/wi-<id>/plan.json.agents/tests/wi-<id>/runs.jsonl

測試規格與執行歷史，讓團隊能累積與重播。

不進版控

%TEMP%\wi-test\<id>\run-<n>

截圖、result.json、comment.html 屬於本次結果，不應塞滿 Git。

WHY IT MATTERS

wi-test 的目的不是取代人工測試，而是把人的時間留給真正需要判斷的地方。

1
重複驗證交給工具

固定流程、權限檢查、回歸測試與曾經出過的問題，可以快速重跑並留下證據。

2
團隊經驗累積下來

PM / SA 回報、補充情境與歷史檢核會逐步沉澱成可重播的測試計畫。

3
判斷仍然交給人

操作體驗、畫面美感、探索式測試、需求合理性與工具無法穩定判斷的情境，仍需要人工驗收。

讓 wi-test 負責「重複驗證與留下證據」，讓人把時間留給「判斷、探索與真正的風險」。
